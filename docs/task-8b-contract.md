## Fixed scope and behavior

Implement an internal bounded production cleanup service and scheduled runner, **no new HTTP endpoint**. Scheduling actually invokes the service through Spring. Reuse account_sync_state.pruned_through, committed_cursor and stored batches/changes. No migration is expected; any schema/dependency/build/config change requires prior Coordinator approval. A small new scheduler-only application.yaml configuration block is allowed as specified below; do not change existing auth/database configuration or secrets.

At service time T, compute one fixed UTC elapsed-time cutoff for the cleanup invocation: **T minus 90 × 86,400 seconds**. Use a controllable clock/time boundary for deterministic tests, with ordinary production UTC defaults; no client business time or token age. A batch is eligible at committed_at <= cutoff; strictly later is retained. Existing sync_changes.expires_at is not authority to delete changes individually.

For each account, prune only a complete contiguous oldest committed prefix strictly after the durable watermark. Stop at the **first ineligible batch**, even if later timestamps are older after clock correction. Operational batch limits may stop sooner, never create a gap. Never allocate/advance committed_cursor, create a batch, change root revision or infer expiry from token age. Unexpected missing required batch history must not be papered over by advancing the watermark.

Delete corresponding change rows, then their parent batches, and advance pruned_through to the last removed committed boundary in the **same real transaction**. No partial batch deletion; no deletion without watermark or watermark without deletion. Account-scoped cleanup transactions serialize with accepted publishers using the same account-row lock and compatible lock ordering (account before sync-state). Concurrent cleanup instances must not regress a watermark or double-apply stale work. Locked/busy accounts may be skipped rather than stall a tick; later ticks retry. Pull retains accepted RR behavior: a reader started before pruning may return a complete old retained view; afterward it sees new watermark/history together. No internal_error caused by normal prune/write/read interleavings.

Retain **sync_cursor_tokens**, including tokens before the watermark: a known old token must still resolve to typed 410 cursor_expired, not become unknown 400. Preserve all sync/resource accepted/rejected identity and original results, domain roots/children, sole active state, root tombstones, identity reservations, catalogue and authentication/credential lifetimes. Do not compact/purge domain/tombstone children in this slice. Skip disabled accounts; account purge and its scheduling belong to Task 9. No deletion of data under unrelated TTLs.

### Bounded scheduling policy

Each tick is finite in accounts and complete batches per account; default targets **100 accounts and 500 batches/account**. These are internal work budgets, not API/product caps. Report a simpler justified choice to Coordinator before implementation if needed. Candidate scanning must not repeatedly select permanently ineligible leading accounts and starve eligible work. Draining backlog happens across ticks. No sleeping inside an account transaction or unbounded all-account/all-history materialization.

Use a configurable fixed delay and initial delay (default **60,000 ms** each), with a scheduler enable switch default true for normal service and false/controlled timing for deterministic tests. Names must clearly identify sync-history cleanup, not auth cleanup. Proposed environment names: `SYNC_HISTORY_CLEANUP_ENABLED`, `SYNC_HISTORY_CLEANUP_FIXED_DELAY_MS`, `SYNC_HISTORY_CLEANUP_INITIAL_DELAY_MS`; corresponding application properties under `sync.history.cleanup`. The exact small configuration block/class boundary is reviewed with Worker's pre-edit design. Configuration contains no secrets. Preserve all existing config values.

A failed cleanup account transaction rolls back entirely and can retry next invocation; successfully committed earlier account transactions need not roll back with a later failure. Do not swallow failure and claim it pruned successfully. Prefer explicit small outcome/progress data where useful, but no framework or user identifiers in logs. The new runner must use sanitized bounded error reporting (no raw SQL, stack trace/request/account/resource/token/payload) and remain callable on later ticks after a failure. Broader pre-existing auth scheduler lifecycle/logging debt is outside this slice.
