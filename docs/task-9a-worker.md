## D9a.1 — amended admission sequence (read starts before irreversible consumption)

The defect in revision 1 was real: Transaction A committed consumption before Transaction B had acquired its streaming connection or established any repeatable-read view, so consumption paid for a mere reservation of a possibly unstarted read. The shared contract requires consumption once the authorized consistent export read starts. The amended sequence establishes the writer-thread consistent read first, then consumes in a separate short transaction, then streams on the already-established snapshot without holding admission locks.

Concrete sequence, all on the servlet async streaming thread inside the `StreamingResponseBody` callback (no `@Transactional` on the controller, because the controller thread is not the writer thread):

1. Strict shape parse only (no database, no Google, no consumption). Structural failures reject here with the approved `400`/`422` mapping. No challenge state changes.
2. Open the streaming connection first: raw `dataSource.getConnection()`, `setAutoCommit(false)`, `setTransactionIsolation(Connection.TRANSACTION_REPEATABLE_READ)`, `setReadOnly(true)`. Wrap it for repository reads as `new JdbcTemplate(new SingleConnectionDataSource(streamConnection, true))` so every chunk read demonstrably uses this one physical connection on this thread. If this acquisition fails (pool exhaustion, async startup failure), reject pre-admission with `503` and consume nothing.
3. On the streaming connection, establish the snapshot with the first read: `SELECT nonce, purpose, expires_at, consumed_at FROM auth_challenges WHERE id=?` without a row lock (early purpose and consumed screen plus the nonce for Google verification), and `SELECT deleted_at FROM accounts WHERE id=?` without a row lock (early liveness screen). Any failure to establish this view (SQL fault, missing rows treated as reject, async failure) rolls the streaming connection back and consumes nothing. The snapshot is now established; this is the consistent read start.
4. Verify Google outside all row locks using the nonce from step 3. Early purpose, consumed, and `clock.instant() >= expiresAt` screens may reject before this call; the final binding decision still waits for step 5. No lock is held across this unbounded remote call.
5. Final consumption on a second, separate short connection: fresh `dataSource.getConnection()` (never the thread-bound `JdbcTemplate`, so it demonstrably bypasses `DataSourceUtils` thread binding), `setAutoCommit(false)`, default isolation, then in order: `SELECT ... FOR UPDATE` on the challenge row with full final revalidation (purpose is `export`, `consumed_at IS NULL`, `clock.instant() < expiresAt` rechecked after all waits), `pg_advisory_xact_lock(hashtextextended(subject, 0))` on the verified subject, binding comparison against the requested account, `SELECT deleted_at IS NULL FROM accounts WHERE id=? FOR UPDATE`, then the conditional `UPDATE auth_challenges SET consumed_at=clock_timestamp() WHERE id=? AND consumed_at IS NULL` requiring exactly one row, then commit and immediately close. This commit is the irreversible admission point. Its lock order (challenge row, subject advisory, account row) is provisional for 9a only and binds no future 9b design.
6. Stream on the already-established streaming connection from step 3: capture `exportedAt` from the injected `Clock`, page root IDs by `id::text COLLATE "C"` in bounded chunks, read each full aggregate through the streaming connection, and write envelope bytes through the cancellation wrapper in D9a.2. The streaming transaction holds no `FOR UPDATE`, advisory, session, credential, or domain write lock at any point.
7. On full successful closure, commit (read-only release) and close the streaming connection. On any post-admission failure, roll it back; the step 5 commit stays durable on its own connection.

Explicit boundary. Pre-admission with no consumption: structural rejection, challenge unfound, wrong purpose, already consumed, expired at the final check, Google failure, binding mismatch, unknown or disabled account at the final check, and any pool, async, snapshot-establishment, or consumption-commit failure. Post-admission with durable consumption: every read, serialization, live-cancellation, transport, or client-disconnect failure after the step 5 commit, including a pre-first-byte independent live-check failure (no bytes released, but the proof stays consumed and the client retries with a fresh challenge). An interrupted stream never rolls consumption back and never resumes on the old challenge because no export is stored.

## D9a.2 — byte-write cancellation wrapper on the independent current view

Between 100-ID chunks is insufficient because one very large aggregate can release many bytes after disablement is observable. The wrapper below checks the independent current view, not the frozen repeatable-read row, immediately before outward byte writes, including inside a large single root and before final closure and flush.

- Mechanism: a small `ExportWriteGate` around the servlet `OutputStream` (used by the Jackson generator). Every write path funnels through `writeChecked(bytes)`. The gate enforces mandatory checks before the envelope start, before each array start, before and after each root element, and before the final `]`/`}` closure and flush, plus a byte-volume throttle inside large elements (for example every 8 KiB or at least every 50 ms, whichever comes first) so a single huge workout cannot stream unchecked.
- Independent view: each check opens a fresh autocommit connection from the raw `DataSource` (`getConnection()`, autocommit true, default isolation), runs `SELECT deleted_at FROM accounts WHERE id=?` with no `FOR UPDATE` and no advisory lock, and closes the connection in a `finally` block. It deliberately bypasses thread-bound `JdbcTemplate` and `DataSourceUtils` by never using the streaming thread-bound template for these checks. Missing row or `deleted_at` set means disabled: throw an internal `ExportCancelled` carrying no payload. A live-check SQL or pool-acquisition failure also aborts the stream; before the first byte it maps to the pre-first-byte error below, and after the first byte it follows the post-byte abort path.
- No blocking account locks are held for the slow client. The streaming snapshot holds no row locks, and each live check is a short lock-free read on its own connection that is closed immediately. Pool impact is bounded: one held streaming connection plus transient checkouts that each live for one indexed primary-key lookup. Acquisition timeouts do not extend the export; they abort it as above.
- In 9a the disablement fixture is controlled test isolation (for example setting `accounts.deleted_at`), and the same seam is re-exercised through the real deletion endpoint in later slices. The 9a check treats any set `deleted_at` or absent account row as cancelled.

## D9a.3 — pre-first-byte status versus post-byte abort in Spring streaming

Chosen mechanism: the controller returns `ResponseEntity<StreamingResponseBody>` but the response is not committed until the first flush inside the callback. A `bytesReleased` flag, set only by a successful first `write`/`flush` to the servlet stream, distinguishes the two paths. The Jackson generator is created with auto-close of the target disabled and, critically, no automatic object or array completion: the `finally` block calls `generator.flush()` at most and never `writeEndArray`, `writeEndObject`, or `close` semantics that would synthesize a syntactically complete document after a failure.

- Pre-first-byte (flag false, `response.isCommitted()` false): reset the uncommitted buffer, set the sanitized status and `application/json` plus `no-store`, and write exactly `{"errorCode":"..."}`. Deletion or disablement observed before any byte uses `404 not_found`; a live-check or pool fault before any byte uses `503 temporarily_unavailable`; unexpected faults use `500 internal_error`. The proof stays consumed when admission already committed; the client retries with a fresh challenge. No export bytes are released.
- Post-byte (flag true or response committed): write nothing further except aborting. Do not append error JSON, do not close the arrays or object, and do not translate the failure into a second status. Close or truncate the stream so the client observes incomplete JSON, which is by definition a failed export.
- Framework surface: exceptions thrown from the streaming callback after commit enter async dispatch and cannot change the committed status. Thrown types carry only the internal gate signal (`ExportCancelled`, IO failure); they never embed the token, proof body, account data, SQL, or stack details. Container or async error logging is sanitized to route template, status class, timing, and a random correlation ID, consistent with the retention logging policy. Controller advice is not relied on for the committed path.

## D9a.4 — final revalidation and honest Google-call bounds

- The early challenge read in D9a.1 step 3 is a screen only. The decision check happens in step 5 after all waits: under the challenge `FOR UPDATE` lock, revalidate purpose equals `export`, `consumed_at IS NULL`, and `clock.instant() < expiresAt`. Expiry during Google verification, lock queueing, or snapshot establishment therefore rejects with `401 invalid_google_credential` and consumes nothing.
- Consumption is the last statement before commit (`UPDATE ... WHERE consumed_at IS NULL`, one row required). Same-challenge races serialize on the row lock; losers observe the consumed marker and reject with `401`, rolling back their own uncommitted streaming snapshot with no bytes. Every rejection path leaves a still-valid challenge unconsumed.
- No bounded-duration claim is made for `GoogleTokenVerifier.verify`: the repository configures no explicit connect or read timeout for the Google certs or token-verification call, so the design verifies outside all database row locks (step 4) and accepts that a stalled provider call delays only that export attempt without holding shared locks. Deterministic tests mock only external Google behavior; real verifier claim and signature regressions stay covered elsewhere. A deployment-level timeout is future operations work, not a 9a code claim.
- No signup is possible on this path: the consumption transaction performs no account insert, no binding insert or update, no session or credential write, and no replay write.

## Addendum R3 — final source-level corrections (authoring still withheld)

This addendum corrects five exact ambiguities. Everything in revision 2 stands except where explicitly corrected below.

1. Streaming connection choice. Accepted: wrapping a raw connection in a new `SingleConnectionDataSource` does not redirect the injected `CanonicalAggregateRepository` (or related repositories), which hold the original `JdbcTemplate`. Explicit choice: the streaming snapshot uses a writer-thread read-only `REPEATABLE_READ` `TransactionTemplate` on the existing `PlatformTransactionManager`, so the existing injected read repositories demonstrably share its `DataSourceUtils`-bound connection on the streaming thread. Final consumption and every live check use raw distinct `DataSource` connections (`dataSource.getConnection()`, never `DataSourceUtils` or the thread-bound `JdbcTemplate`, try-with-resources, closed immediately) outside that thread-bound transaction. No raw-B repository path is retained, so no narrow read adapter is needed and no write algorithm is touched. Google verification runs before entering the RR template (preliminary raw-autocommit nonce screen, then verify with no transaction open), so the unbounded provider call never holds the RR connection; the snapshot is still established before the consumption commit.

2. Final recheck placement and in-doubt commit. The final freshness check sits immediately before the conditional `UPDATE`, after both the subject-advisory wait and the account `FOR UPDATE` wait, not merely at the `SELECT ... FOR UPDATE`. Under the locked challenge row it re-asserts: stored nonce equals the Google-verified nonce, purpose is `export`, `consumed_at IS NULL`, and a fresh `Clock` read satisfies `now < expiresAt`. Rejection rolls back with no consumption. If the commit itself throws an uncertain failure (connection loss or timeout during commit), the outcome is in-doubt: report failure with no bytes, treat consumption as unknown, require a fresh proof, and never restore or reuse the challenge.

3. No early 404 oracle. Snapshot-establishing account and binding reads are screens only and never produce a `404` from an unverified `accountId`. The final `404` is returned only after verified Google proof: the requested account must match the binding both in the RR snapshot view (`SELECT account_id FROM google_identity_bindings WHERE google_subject=?`) and in the locked consumption connection (binding re-selected under locks) with a live account row. Within 9a scope the `google_subject` primary key to account mapping is immutable (no 9a rebinding path; detachment is 9b), so both views agree, but both checks are still performed rather than relying on that label.

4. Generator, byte-tracking, and logging scope. On any failure or cancellation the `finally` block never flushes pending generator bytes and never finishes arrays or the envelope object. The generator is configured with Jackson `AUTO_CLOSE_JSON_CONTENT` and `AUTO_CLOSE_TARGET` disabled. Commit tracking is conservative: a `bytesAttempted` flag is set before each outward write attempt, and the reset/status path is allowed only when `!bytesAttempted && !response.isCommitted()`, because an `IOException` may already have released bytes before returning. Async failures are sanitized on the new export path only (route template, status class, timing, correlation ID; no SQL, token, proof, or domain causes forwarded). No global container-logging compliance is promised; system-wide logging remains Task 10.

5. Catalogue source, segment guards, and pool limit. Explicit choice: read and validate the pinned installed version from `catalogue_versions` on the existing RR view instead of touching the private `ResourceBrowseService.CATALOGUE_VERSION` or the importer. Every outward segment funnels through the gate at a maximum of 8 KiB per segment; first-write and final-closure checks are mandatory and a time throttle may only add checks, never skip them; no flush occurs on failure. Pool discipline: one held RR connection per in-flight export plus transient checkouts with a bounded acquisition timeout that fails closed (pre-byte maps per the D9a.3 boundary with consumption preserved; post-byte aborts), every checkout released in `finally`. This is documented as a capacity and latency limit on concurrent exports under a finite pool, not a resource-bound guarantee.

Corrected order: strict parse, preliminary nonce screen on raw autocommit, Google verify with no locks held, enter writer-thread RR `TransactionTemplate` (snapshot screens, binding screen for the verified subject, catalogue-version read, `exportedAt` capture), locked consumption on a raw separate connection (challenge `FOR UPDATE`, subject advisory, account `FOR UPDATE`, final nonce/purpose/unconsumed/expiry recheck, conditional consume, commit, close), independent pre-first-byte live check on raw autocommit, then gated streaming with 8 KiB segments through final closure, releasing the snapshot on success and aborting with incomplete JSON on failure.
