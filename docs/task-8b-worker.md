## Production boundaries for QA and review

- `sync.SyncHistoryPruningService.pruneExpiredHistory()` is the cohesive callable service entry point used by the real scheduler and available directly to integration tests. It samples the injected existing `Clock` bean (`serviceClock`) once, subtracts exactly `Duration.ofDays(90)`, and returns bounded `CleanupProgress` counts on success. Defaults are 100 candidate accounts per invocation and 500 batches/account.
- `persistence.SyncHistoryPruningRepository.findCandidates(cutoff, limit)` uses one bounded query ordered by the timestamp of each account's next required batch and account UUID. It excludes disabled accounts and heads later than the cutoff; a missing required head is selected as corruption, not mistaken for an empty/expired account. No scan loop or process-local fairness/correctness state is used.
- Coordinator finding F8b.1 was addressed narrowly in `readPrefixWindow`: a materialized ordered CTE first limits batches to `batchLimit` and `committed_cursor`, then joins/counts change rows. Contiguous/nonempty validation, deletion counts, watermark update, account-first lock and independent `REQUIRES_NEW` transaction are unchanged. No unrelated production path changed in this correction.
- `SyncHistoryPruningRepository.pruneAccount(...)` executes each account in `REQUIRES_NEW`. It locks the enabled account row first with `FOR UPDATE SKIP LOCKED`, then locks sync state and rechecks current history. It selects at most 500 ordered batches, validates contiguous cursors and nonempty complete batches, stops at the first timestamp later than cutoff, deletes changes then batch parents, and advances only `pruned_through` in the same transaction. Count mismatches/corruption throw and roll back that account. Previously committed account transactions remain committed. A busy/disabled account is reported as skipped.
- `sync.SyncHistoryCleanupScheduler.runCleanup()` is the actual scheduled entry point. Its bean is conditional on `sync.history.cleanup.enabled` (default true), fixed-delay and initial-delay defaults are 60,000 ms. It reports only a fixed sanitized failure message and does not attach exception details; a failed account is retried by a later tick.
- `src/main/resources/application.yaml` adds only the approved scheduler block: `SYNC_HISTORY_CLEANUP_ENABLED`, `SYNC_HISTORY_CLEANUP_FIXED_DELAY_MS`, `SYNC_HISTORY_CLEANUP_INITIAL_DELAY_MS`. No migration, dependency, build, auth configuration, API endpoint, cursor-registry deletion or replay/domain mutation was added.
